Python Compiler — Architecture & Workflow

A hand-written compiler that parses Python source, runs semantic analysis, extracts runtime context (ContextExtractor), and renders Flask/Jinja2 templates into static HTML. The project also supports HTML/Jinja2 and CSS, and can serve the generated output through a built-in web server (--serve) that exposes a generic CRUD API (/api/<collection>) for any top-level list of dictionaries — not just products.

End‑to‑End Pipeline Overview

Phase 1 Lex & Parse → Phase 2 Build AST → Phase 3 Semantic Analysis → Phase 4 Context Extraction → Phase 5 Render HTML

Phase 1 — Lexing & Parsing

ANTLR 4.13.2

The source file is fed through the ANTLR-generated PythonLexer (tokeniser) which produces a CommonTokenStream. The PythonParser then builds a Concrete Syntax Tree (CST) using the grammar rules defined in grammars/PythonParser.g4. 

// App.processFile() — relevant snippet
CharStream input     = CharStreams.fromFileName(path);
PythonLexer lexer    = new PythonLexer(input);
CommonTokenStream tokens = new CommonTokenStream(lexer);
PythonParser parser  = new PythonParser(tokens);
parser.addErrorListener(new CustomErrorListener());
ParseTree tree       = parser.prog();   // ← CST built here

Key files: PythonLexer.java, PythonParser.java, PythonLexerBase.java (custom indentation, brace tracking, NEWLINE handling), CustomErrorListener.java.

Phase 2 — AST Construction

~32 specialised visitors

The CST is walked by a family of visitor classes, each responsible for a single grammar domain. Every visitor creates or dispatches to create hand‑crafted AST nodes (in src/ast/). The symbol table is populated inline during this phase. 

// CompoundStatementVisitor acts as the dispatcher
switch (ctx) {
    case AssignmentStatementContext a  → visitAssignmentStatement(a);
    case IfStatementContext i           → build new IfStatement(...);
    case ForLoopStatementContext f      → new ForLoopVisitor().visit(f);
    case FunctionDefinitionContext fn   → enterScope(); build new FunctionDefinition(...); exitScope();
    case AtomExpressionContext a        → new AtomExpressionVisitor().visit(a);
    case ReturnStatementContext r        → new ReturnStatementVisitor().visit(r);
    case ImportStatementContext i        → build new ImportStatement(...);
    case GlobalStatementContext g        → build new GlobalStatement(...);
    default                               → UniversalPythonVisitor().visit(ctx);
}

Key files: ProgramVisitor.java, StatementVisitor.java, CompoundStatementVisitor.java, AssignmentStatementVisitor.java, AtomExpressionVisitor.java, AtomVisitor.java, ConditionVisitor.java, ForLoopVisitor.java, ArithmeticExpressionVisitor.java, ComplexExpressionVisitor.java, ReturnStatementVisitor.java, FunctionParametersVisitor.java, ArgumentListVisitor.java, ArgumentVisitor.java, KeyValueVisitor.java, TemplateLiteralVisitor.java, UniversalPythonVisitor.java, and all ast/ node classes.

Phase 3 — Semantic Analysis

Rule-based walker

The SemanticAnalyzer walks the entire AST and applies a set of SemanticRule implementations to every node. Each violation surfaces as a named exception (semantic/errors/*.java), and the CLI reports it as Semantic error detected "TypeError": …. One compilable example per error type lives in samples/<ErrorName>/.

RuleWhat it checksError raised
TypeRuleType inference; detects mismatches (e.g. string + int)TypeError
UndefinedVariableRuleFlags Name nodes not found in symbol tableUndefinedVariableError or ScopeError
UndefinedFunctionRuleFlags FunctionCall to unknown functions (30 builtins whitelisted)UndefinedFunctionError
NotIterableRuleFlags for-in over a non-iterableNotIterableError
DuplicateFunctionRuleFlags duplicate def namesDuplicateFunctionError
ReturnOutsideFunctionRuleFlags return at module level (function-scope aware)ReturnOutsideFunctionError

So the six rules produce seven of the eight named errors. The eighth, MissingFlaskVariableError, is not a rule — it is raised by semantic/jinja/FlaskTemplateChecker.java when a template variable was never passed to render_template. That is why samples/ contains 9 folders: one per error type (8) plus CombinedErrors/, a single file that triggers several errors at once as a demo. 

// SemanticAnalyzer.walk() — apply every rule to the node, then recurse per type
for (SemanticRule rule : rules) {
    rule.apply(node, symbolTable, reporter);
}
switch (node) {                  // Program, Statement, If, While, ForLoop, FunctionDef…
    case IfStatement i         → walk(i.getStatement(), reporter);
    case FunctionDefinition f  → walk(f.getFunctionBody(), reporter);
    default                    → // leaf
}

Key files: SemanticAnalyzer.java, SymbolTable.java, SymbolTableManager.java, SymbolEntry.java, ErrorReporter.java, rules/*.java.

Phase 4 — Context Extraction & HTML Rendering

Flask project mode

The ContextExtractor walks the Python AST and extracts the runtime data needed to render the templates (route functions, context variables, url_for targets, collection/list data). A JinjaRenderer then renders each template (given its HtmlContent AST) to static HTML, which the OutputWriter writes into output/ together with support files (app.py, styles.css, script.js, templates/). Reports (semantic report, generation log, AST JSON dumps) are written to compiler_output/. 

// processFlaskProject() — relevant snippet
ContextExtractor extractor = new ContextExtractor();
Map<String, Object> context = extractor.extract(program);       // Phase 4
Map<String, String> routes   = extractor.extractRoutes(program);

JinjaRenderer renderer       = new JinjaRenderer(context, templateMap, routes);
String renderedHtml           = renderer.render(htmlContent);
outputWriter.writeHtmlFile(outputName, renderedHtml);            // Phase 5

In serve mode (--serve), the generated output/ directory is continuously regenerated by a ProjectWatcher whenever a source file changes, and a built-in CompilerWebServer serves the pages on the same origin (no CORS). For a single file (non-Flask) invocation, rendering is skipped — only the Python AST + semantic analysis are printed; .html/.j2/.css files are written to a local generated/ folder.

Generic CRUD API

The server discovers editable collections from the compiled context: any top-level variable whose value is a list of dictionaries that each carry a numeric "id" (e.g. products, posts, books). Each one gets its own endpoint /api/<collection>:

EndpointMethodAction
/api/<collection>GETList all records (JSON array, types preserved)
/api/<collection>POSTCreate a record (id = max + 1) → 201
/api/<collection>/<id>GETFetch one record
/api/<collection>/<id>PUTUpdate fields from the form → 200
/api/<collection>/<id>DELETERemove a record → 204

PythonDataStore keeps app.py as the single source of truth: every mutation is written back into the matching literal, then CompilationSnapshot.rerender() re-renders the templates with a merged live context (all editable collections from their stores, everything else from the last full compile). Whole numbers are normalised to integers in JSON/rendered output, floats/booleans/strings keep their type. Everything else in the context (plain dicts, string lists, scalars) is read-only. Errors are reported as JSON (404/400/405/500), and an SSE stream at /events pushes regenerated / compiler-error events.

Key files: generator/ContextExtractor.java, generator/JinjaRenderer.java, generator/OutputWriter.java, app/CompilerWebServer.java, app/PythonDataStore.java, app/DataRecord.java, app/CompilationSnapshot.java, app/ProjectWatcher.java.

Key Design Decisions

DecisionRationale
Visitors for CST→AST, renderers operating on AST nodes Double‑dispatch. ANTLR visitors handle grammar‑specific logic during tree conversion; the context extractor and Jinja renderer walk the finished AST instead of a monolithic switch.
Symbol table populated during AST construction No separate pass needed. The visitor building the AST already knows what symbols are being defined (function names, parameters, globals) and can enter/exit scopes immediately.
Dynamic type inference in AssignmentStatementVisitor Keeps the symbol table useful for semantic checks without requiring a full Hindley‑Milner type system. Infers Integer, Float, String, Boolean, List, Dict.
Context extraction decoupled from rendering ContextExtractor gathers route data and context variables in one pass; JinjaRenderer only consumes them. This separation makes it easy to re-render static HTML after any data change: CompilationSnapshot keeps the last successful compile and rerender(liveContext) re-renders it without re-lexing/re-parsing.
app.py is the single source of truth For the web runtime (PythonDataStore), CRUD mutations on any collection are written back into the matching top-level literal of app.py, then the templates are re-rendered through the compiler — no second data model to keep in sync, and types (numbers, booleans, strings) survive the round trip.
Editable collections are discovered, not hard-coded The server inspects the compiled context and exposes /api/<collection> for every list-of-dicts variable with a numeric "id" (products, posts, books, …). No field set is hard-wired; non-list data stays read-only.
UI mutations re-render with a merged context After a browser write, every editable collection is overlaid onto the snapshot context before re-rendering, so templates that read several collections (e.g. students + teachers) are regenerated consistently in one pass.
